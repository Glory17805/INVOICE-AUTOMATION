The architecture

Two containers on one App Service plan, a managed PostgreSQL server, and a file share for the workbooks. Central India, so Indian tax records stay in-country.

What is built

All of it committed and pushed to Glory17805/INVOICE-AUTOMATION. Nothing below is scaffolding — each piece was run and checked.

PostgreSQL, without giving up SQLite

The database layer now picks its engine from DATABASE_URL. Tests keep the speed of a fresh SQLite file; the deployment gets an engine that survives its own filesystem. One schema template rather than two copies, so a table cannot be added to one engine and forgotten in the other — the dialect differences are held to three substitutions.

backend/app/db.pytools/migrate_to_postgres.py
356 tests pass on both engines. Verified against a live PostgreSQL 16 in Docker, each test in its own schema.

Three things this caught

Each would have failed a first deployment, and each is cheaper to find on a laptop than in a crash-looping container.

The frontend bound the container’s own loopback

server.py defaults to 127.0.0.1, which is right on a laptop and useless in a container: traffic arriving on eth0 from the port forward is refused by a process listening only on loopback.

curl: (52) Empty reply from server — reads like a crashed app, not a bind address

Readiness described a database it never opens

The probe reported the SQLite path unconditionally, so a PostgreSQL deployment was described by a file it does not use — on the one screen you read to decide whether a deployment came up. It now names the actual server, password stripped.

was: /data/store.db  →  now: postgresql://postgres@db:5432/gst

The API will not start without the master workbook

Correct behaviour — a GST system with no register to write into has nothing to offer — but it makes the workbook a startup dependency. In Azure it must be on the file share before the container starts, or the app crash-loops on a missing path. The deploy script uploads it first for exactly this reason.

What you need to do

Five steps, in order. The first two are the only reason I could not finish this myself: installing the Azure CLI needs administrator rights, and signing in needs a browser.

Install the Azure CLI

I tried both routes that do not need administrator rights. winget registered nothing, and the pip install left only partial dependencies. The MSI is the reliable route and it needs an elevated prompt.

# In a PowerShell window opened with "Run as administrator"
winget install --id Microsoft.AzureCLI -e

Sign in to Azure

Opens a browser. Afterwards the credentials sit in ~/.azure and I can use them for everything else — so once this is done, tell me and I will run the deployment.

Deal with the Claude API credits

Unrelated to Azure, but it decides how well the deployed system reads invoices. Your key authenticates correctly; the organisation behind it has no spendable balance, so every read falls back to the offline reader. Ask your administrator for credits on the org, or — if credits already exist — a non-zero spend limit on your key’s workspace, which costs nothing extra.

The deployment works without step 5

The offline reader is not a stub. It parses the label-then-value layout your billing software emits, reads both GSTINs, place of supply, HSN and the totals row, and now does OCR for scans. It never guesses: anything unreadable stays null, and every offline-read document goes to Quick Review rather than being auto-confirmed.

So you can deploy, upload, review and post today. It simply means more manual checking per invoice until credits arrive — and re-reading afterwards will redo them properly.

Decisions worth knowing

Why move off SQLite at all?

Every persistent disk App Service offers is SMB-backed, and SQLite’s WAL mode uses shared-memory mapping that SMB does not support. Turning WAL off makes it technically work and leaves a database of tax records one dropped SMB connection away from corruption. singleton.py already goes to some length to prevent a silently lost tax row; accepting that same risk from the storage layer would have been inconsistent.

Why App Service rather than Container Apps?

Container Apps is built around scaling replicas, and this application cannot have two. App Service pins to one instance cleanly and runs both containers on a single plan.

Why does email need a database extension?

Accounts are looked up with WHERE email = ? and rely entirely on the column collation to match Priya@ against priya@. SQLite spells that COLLATE NOCASE; PostgreSQL spells it CITEXT. Using the extension rather than rewriting those lookups keeps both engines behaviourally identical — which is the whole basis for trusting a SQLite test run to say anything about production.

It has to be allowlisted through the azure.extensions server parameter, which the Bicep template does. Without that, the very first request would fail.

Why build for linux/amd64 explicitly?

App Service runs amd64. A machine defaulting to ARM would push an image that cannot start there, and the failure appears as a container exiting immediately with no useful log.
