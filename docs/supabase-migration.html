Before anything: the free-tier catch

This one decides whether Supabase suits this project at all, so it comes first.

Free projects pause after 7 days without activity

A paused project stops answering. You restore it by hand from the dashboard, and it takes a minute or two to come back.

That matters here more than it would for most apps: GST returns are monthly. A tool opened around the filing date and left alone in between will be paused almost every time you go to use it. The database being asleep is exactly when you need it.

There are three honest ways around it, and you should pick one before migrating:

OptionCostWhat it means
Accept the pause₹0Unpause from the dashboard when you sit down to file. One click, a minute's wait, once a month.
Keep it warm₹0A scheduled query every few days. A GitHub Actions cron doing one SELECT 1 is enough, and Actions is free for public repos.
Supabase Pro~$25/moNo pausing, daily backups, more storage. Far more than this project needs.

The keep-warm cron is what I would do — it costs nothing and removes the problem entirely. There's a ready-made workflow at the end of this guide.

Part oneDatabase

The easiest win in this whole guide, because the work was already done.

When the app moved to Azure it had to leave SQLite, so db.py was rewritten to speak both engines from one schema. It picks PostgreSQL whenever DATABASE_URL is set. Supabase hands you exactly that string, so pointing the app at Supabase is configuration, not code.

Create the project

At supabase.com, new project, region South Asia (Mumbai). Save the database password it generates — it is shown once.

Take the session-pooler connection string

Project Settings → Database → Connection string. Pick Session pooler, not Transaction pooler and not Direct.

# Session pooler - port 5432, IPv4, keeps prepared statements working
postgresql://postgres.[ref]:[password]@aws-0-ap-south-1.pooler.supabase.com:5432/postgres?sslmode=require

This choice is not cosmetic, and it is the thing most likely to waste your afternoon — see the note below.

Move your existing data

The tool for this is already in the repo. It reads the SQLite file and writes through the application's own schema, so the destination is built exactly as the app expects.

cd backend
$env:DATABASE_URL = "<the session pooler string>"
python -m tools.migrate_to_postgres --sqlite data/store.db

It refuses to run twice rather than doubling your audit trail. Pass --replace if you genuinely need to re-run it.

Point the deployment at it

Set it as a Container Apps secret, so the password is not sitting in plain configuration.

az containerapp secret set -g rg_internship -n iragst-api \
    --secrets database-url="<the string>"

az containerapp update -g rg_internship -n iragst-api \
    --set-env-vars DATABASE_URL=secretref:database-url \
    --remove-env-vars GST_SQLITE_PATH GST_DB_MIRROR GST_DB_MIRROR_INTERVAL GST_SQLITE_JOURNAL

Check it took

/api/ready reports which database it is actually talking to, with the password stripped. It should now name the Supabase host instead of a file path.

curl https://iragst-api.<env>.azurecontainerapps.io/api/ready

"database": { "ok": true,
  "detail": "postgresql://postgres.[ref]@aws-0-ap-south-1.pooler.supabase.com:5432/postgres" }

Use the session pooler, not the transaction pooler

Supabase offers three connection strings and two of them will bite you here. The transaction pooler (port 6543) runs pgbouncer in transaction mode, which does not support the prepared statements psycopg uses by default — you get intermittent prepared statement "_pg3_0" already exists errors that look like application bugs. The direct connection is IPv6-only on the free tier, and Container Apps will simply fail to reach it.

The session pooler is IPv4 and holds one connection per session, which is exactly what a single-instance app wants.

What you can delete afterwards

Once the deployment is on Supabase and you have confirmed a post works, app/dbsync.py, its seven tests and the three call sites in main.py and pipeline.py all become dead weight. That is around 170 lines of workaround that existed for one reason, which no longer applies.

Keep the SQLite path itself — it is what the test suite runs on, and what makes a local checkout work with no services at all.

Part twoDocument storage

Right for the PDFs. Wrong for the workbook, and the difference matters.

The app touches durable files in three roles, and they are not alike:

WhatWhere nowAccess patternSupabase Storage?
Uploaded PDFsincoming/Write once, read a few times, then move.Yes — ideal
Archived sourcesarchive/Write once, read rarely, keep forever.Yes — ideal
Period workbooksworkbook/Read, modify and rewrite on every single post.No

Why the workbook must stay on a filesystem

openpyxl works on paths, not streams: load_workbook(path) then wb.save(path). Object storage has no paths, so every post would become download → open → modify → save → upload, with the whole register crossing the network twice.

That is slow, and worse, it reintroduces a race the current design closed: between the download and the upload, the file on the server is stale. The app is single-instance so the window is narrow, but "narrow" is not the standard you want for the file holding filed returns. Leave the workbook on the Azure Files share, which handles whole-file writes perfectly well.

Create a private bucket

Storage → New bucket, named documents, not public. These are invoices with real GSTINs and amounts; a public bucket is a directory listing of your client's trade.

Add the client

# backend/requirements.txt
supabase>=2.15,<3.0

Use the service-role key from Project Settings → API, not the anon key. The backend is trusted; the browser never sees this key.

Write one module, change nothing else yet

Put the storage behind the same shape the code already uses, so the call sites change as little as possible.

# backend/app/docstore.py
from pathlib import Path
import os, tempfile
from supabase import create_client

BUCKET = "documents"

def _client():
    return create_client(os.environ["SUPABASE_URL"],
                         os.environ["SUPABASE_SERVICE_KEY"])

def put(key: str, data: bytes) -> str:
    """Store bytes and return the key they can be fetched by."""
    _client().storage.from_(BUCKET).upload(
        key, data, {"content-type": "application/pdf", "upsert": "true"})
    return key

def fetch_to_temp(key: str) -> Path:
    """Download to a real file, because pypdf and OCR want paths."""
    data = _client().storage.from_(BUCKET).download(key)
    handle = tempfile.NamedTemporaryFile(suffix=Path(key).suffix, delete=False)
    handle.write(data); handle.close()
    return Path(handle.name)

def move(old: str, new: str) -> str:
    """Archive without pulling the bytes down and back up."""
    _client().storage.from_(BUCKET).move(old, new)
    return new

def signed_url(key: str, seconds: int = 300) -> str:
    """A link the review pane can load, that expires."""
    return _client().storage.from_(BUCKET).create_signed_url(
        key, seconds)["signedURL"]

Keep stored_path as the seam

Documents already carry a stored_path field. Let it hold an object key instead of a filesystem path and most of the code stops caring which it is. The three places that open the file are the ones to change — wrap each in fetch_to_temp and delete the temp afterwards.

Migrating old rows is a one-off: upload each existing file under the same name, then rewrite the field.

Serve previews by signed URL

The review pane currently streams the PDF through the API. A signed URL lets the browser fetch it from Supabase directly, which takes the load off a container that scales to zero. Remember the frontend's connect-src must then allow the Supabase host, or the browser blocks it silently.

Part threeAuthentication

The one I would leave alone, and the reasoning is about cost against benefit rather than about Supabase.

Supabase Auth is good. The question is not whether it works — it is what replacing a working system costs here, and what you get back.

What is already built

PieceSizeAlready handles
accounts.py24 functionsscrypt hashing, sessions, roles, password reset, session listing and revocation
auth.py11 functionsbearer tokens, the admin/user dependencies, database-backed login throttling
Routes19signup, login, logout, reset, password change, user administration
Protected handlers35every one declares its own access requirement
Audit trailwoven throughevery action recorded against the account that took it

What the swap would cost

All 35 protected handlers keep working only if require_user and require_admin return the same shape, so the honest version of this migration is: verify a Supabase JWT instead of looking up a session row, and keep everything downstream identical.

# the smallest possible version of the change, in auth.py
import jwt  # PyJWT

def caller(request: Request) -> dict | None:
    token = bearer_token(request)
    if not token:
        return None
    try:
        claims = jwt.decode(token, os.environ["SUPABASE_JWT_SECRET"],
                            algorithms=["HS256"], audience="authenticated")
    except jwt.PyJWTError:
        return None
    # Roles are not in Supabase Auth - they live in a profiles table you own,
    # or in app_metadata that only the service key can write.
    return {"id": claims["sub"], "email": claims.get("email"),
            "role": claims.get("app_metadata", {}).get("role", "user")}

That part is genuinely small. The rest is not:

Also neededWhy
Frontend rewrite of the sign-in flowsupabase-js, token refresh, and a session that can expire mid-edit rather than on a fixed clock.
A profiles tableSupabase Auth has no notion of your admin/user roles, or of the approval state.
Retiring 19 routesSignup, login, reset and user administration all move to Supabase, and the Admin screen has to talk to it instead.
Reworking the audit trailIt records a local user id. Those ids change, and the history must still resolve to a person.
Migrating existing accountsscrypt hashes cannot be imported. Everyone resets their password once.
Re-testingA large share of the 365 tests touch accounts or sessions.

What you would gain

Real things, worth naming honestly: password-reset emails that actually send (today the app generates a reset link and has no mail sender), sign-in with Google, multi-factor authentication, and one less thing you maintain.

Weigh that against the system having two users, one of whom is you. Password-reset email is the only item on that list you are likely to miss, and it is a much smaller job to send mail from the existing reset flow than to replace the flow.

If you do want it, do it last

Database and storage are independent of this and can go first without committing you to anything. Auth is the one that touches the frontend, the audit trail and most of the test suite at once — so it wants to be a deliberate piece of work, not a step in a migration that has already moved two other things the same week.

Where that leaves the architecture

Doing parts one and two, and leaving part three.

The keep-warm workflow

This is the piece that makes the free tier usable for a monthly task. It runs every three days and costs nothing.

# .github/workflows/keep-supabase-awake.yml
name: Keep Supabase awake

on:
  schedule:
    - cron: "0 6 */3 * *"   # every three days, well inside the 7-day window
  workflow_dispatch:

jobs:
  ping:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: python -m pip install "psycopg[binary]"
      - name: One query is enough
        env:
          DATABASE_URL: ${{ secrets.SUPABASE_DATABASE_URL }}
        run: |
          python -c "
          import os, psycopg
          with psycopg.connect(os.environ['DATABASE_URL']) as c:
              print('awake:', c.execute('select now()').fetchone()[0])
          "

Suggested order

Database first — it is half an hour and deletes the dbsync workaround. Live with it for a filing cycle before touching anything else, because that is when a paused project or a pooler problem would show itself.

Storage second, once you trust the database. Auth only if password-reset email turns out to be something you actually want.
